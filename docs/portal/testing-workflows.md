# Testing workflows and design assumptions

Private production workflows were **never observed** (see `portal-safety-log.md`). The workflows below are coherent designs for browser-agent testing. They are not claims about how the production portal behaves.

## Accounts and roles

| Username | Display name | IPA memberships (role) | Intended use |
|---|---|---|---|
| `demo.user` | Demo User | DEMO IPA (provider_staff), Demo Empty IPA (provider_staff) | Provider office: submit/edit/cancel requests, upload, notes |
| `demo.reviewer` | Demo Reviewer | DEMO IPA (reviewer) | Utilization review: approve / modify / deny / defer |
| `demo.admin` | Demo Admin | All four demo IPAs (admin) | Everything, incl. Hospital Admin, admin cancel/delete, large dataset |
| `demo.viewer` | Demo Viewer | DEMO IPA (read_only) | Read-only and permission-denied states |
| `demo.other` | Demo Other IPA User | Demo Community Network (provider_staff) | Organization isolation |

Usernames map to `<username>@example.invalid` Supabase Auth users. Local password: `MedPointDemo!2026` (hosted password is set at seed time; see README).

## Sign-in sequence (user-described; production 2FA screen not observed)

1. Username + password. The **DEMO TEST CAPTCHA** checkbox appears once a password is entered and must be checked. It is a labeled test control, not a real challenge.
2. **Sign in** calls Supabase `signInWithPassword` and creates an aal1 session.
3. **Email verification:** `mp_begin_verification()` generates a random 6-digit code per Auth session, stores only a bcrypt hash in `mp_login_challenges`, and writes a **test-mode message** to `mp_demo_outbox`. **No e-mail is sent.** Read the code from **Open demo test mailbox** on the verification screen, or from the account menu.
4. `mp_verify_login_code(code)`: wrong codes count down from 5 attempts, then lock; codes expire after 10 minutes; **Resend code** issues a new code (max 10 messages per session). Success marks the session verified.
5. Every data RLS policy requires a verified session, so an unverified session sees no records even if it calls the API directly.

## Authorization lifecycle

```
draft ──submit──▶ requested ──approve──▶ approved ──(admin) cancel──▶ cancelled
  │                 │  ├─modify (approved units < requested)──▶ modified ──(admin) cancel──▶ cancelled
  delete            │  ├─deny (reason)──▶ denied
                    │  ├─defer (reason)──▶ deferred ──resubmit (edit form)──▶ requested
                    │  │                      ├─approve / modify / deny
                    │  │                      └─cancel (reason)──▶ cancelled
                    └──cancel (reason)──▶ cancelled
```

- Status codes follow the observed status dropdown (`1 - Approved`, `2 - Modified`, `3 - Denied`, `4 - Deferred`, `6 - Cancelled`, `7 - Requested`). `0 - Draft` is a mock addition.
- Submission requires an eligible member and a clinical summary of at least 20 characters; drafts do not.
- Approve/modify set Authorization Date to today and Expiration Date to +90 days when empty.
- Decisions send the record's `updated_at`; a stale value fails with "This authorization changed since you opened it" (conflict testing).
- Every transition writes `mp_activity_events` with actor, from/to status, and reason. These appear in the detail timeline and in the Activity Log.
- Provider staff may delete only drafts; admins may delete any authorization (its notes and attachments go with it).

## Attachments and documents

- Private bucket `mp-demo-documents`; objects live under `<org_id>/<document_id>/<file>`; forms under `shared/forms/`.
- Allowed: PDF, TXT, PNG, JPEG up to 5 MB (bucket-enforced and client-validated).
- Read: any member of the IPA. Upload: admin/reviewer/provider_staff. Delete: the uploader or an IPA admin.
- Seeded files are deterministic synthetic PDFs/TXTs regenerated by the reset command. Use only synthetic files for uploads (`tests/fixtures/`).

## Consult notes

Notes attach to an authorization and its member. Any writer in the IPA can add; only the author or an IPA admin can edit or delete. A note's member must match its authorization's member (enforced by trigger).

## Hospital Admin (invented path)

Production showed a locked "Hospital Admin" control with no link. The demo implements an admin-only inpatient census: record an admission (member + hospital) or a discharge. The changes are reflected in **Members Hospitalized**.

## Datasets

| IPA | Contents | Purpose |
|---|---|---|
| DEMO IPA — SYNTHETIC ORGANIZATION | 24 providers, 120 members, 260 authorizations (all statuses), 300 claims, 30 documents, 60 notes | Main workflows |
| Demo Community Network | 10 providers, 40 members, 40 authorizations, 40 claims, 30 documents, 20 notes | Isolation |
| Demo Large Volume IPA (load test) | 40 providers, 2,000 members, 6,000 authorizations, 6,000 claims | Large dataset / pagination |
| Demo Empty IPA (no records) | none | Empty states |

Dates are relative to the reset day, so "Today / Last 7 / Last 30 Days" filters always have matches. Identifiers use `DEMO-` prefixes (`DEMO-AUTH-000001`, `DEMO-MEM-000001`, `DEMO-NPI-000001`, …). Records created through the UI start at `…-900001`.
